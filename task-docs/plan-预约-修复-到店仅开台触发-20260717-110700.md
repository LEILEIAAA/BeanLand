# plan-预约-修复-到店仅开台触发

## 目标
「已到店(arrived)」状态只能由开台触发;未开台的预约保持「已确认(confirmed)」。
消除座位管理(座位板)与预约管理数据对不上的问题。

## 现状(排查结论)
- 座位板「预约 N」按座位数统计 confirmed/arrived 的座位;预约管理默认按预约单+状态标签。
- `arrived` 在座位板算「活跃预约/待开台」,在预约管理却归入 `ENDED_STATUSES`(已结束),归类相反。
- 今日实测:1 张 `arrived` 单占 2 座(F2-C1、F2-C2),但无 active session(未真正开台)→ 座位板显示「预约2」,预约管理默认「待确认」看不到 → 对不上。
- `arrived` 有两条触发路径:
  1. `adminUpdateAppointment` action='arrive'(`handleArrive`)—— 不开台即可标到店【要删除】
  2. `adminStartSeatSession` → `resolveArriveOnStart`(开台时 confirmed→arrived)【保留】
- 前端已无任何 `action:'arrive'` 调用,手动路径是残留。

## 改动方案
1. `cloudfunctions/adminUpdateAppointment/index.js`:删除 `handleArrive`、`syncArrivedOccupancies`、`action === 'arrive'` 分支。
2. `cloudfunctions/adminUpdateAppointment/appointmentRegistration.js`:`TRANSITIONS` 移除 `arrive`。
3. `miniprogram/utils/appointmentRegistration.js`:`TRANSITIONS` 移除 `arrive`(前后端一致)。
4. 数据修复脚本:扫描 `status=arrived` 且 seatIds 未出现在任何 active seat_session 的单 → 回退 `confirmed`(清 arrivedAt)。

## 不改
- `resolveArriveOnStart`(开台转 arrived)保留。
- `ENDED_STATUSES` 不动:开台后 arrived 座位为 in_use、不再计入座位板预约数,归类不再冲突。
- `STATUS_LABEL.arrived` 保留(开台后仍需展示「已到店」)。

## 风险
- 历史 arrived 单若确实已开台(seatIds 命中 active session)不应回退 → 脚本按 seatId 交叉 active session 排除。
- seat_sessions 不含 appointmentId,只能按 seatId 关联,存在极小误判可能(同座被其他会话占用)→ 打印明细人工可核。

## 验证思路
- 部署云函数后,重跑 diagnose 脚本:arrived 单应为 0(或仅开台中的),座位板预约座与预约管理「已确认」单对得上。
