# 座位预约制度设计规格

> 日期：2026-07-14  
> 状态：已确认（用户选择推荐方案并要求执行）  
> 范围：用户端选座预约 + 店主端座位态看板；承接现有固定时段与座位计时

## 1. 背景与目标

### 现状

- 用户预约：选套餐 / 日期 / 固定时段 / 人数，提交后生成摘要；**不选座位**。
- 店主：预约列表 + 桌号级计时骨架；桌号来自 seed（W/A/L/E）。
- MVP 原文写明「第一版不做复杂座位图」。

### 目标

建立基于**座位**的预约制度：

1. 用户能看到目标时段内座位的空闲 / 预约 / 不可约情况。
2. 用户可**点对点选座**完成预约。
3. 店主能看到更完整的座位经营态（含体验中剩余时长、维护锁座）。

### 非目标（本版不做）

- 连续任意开始时间预约
- 跨桌散座、拼陌生人桌
- 支付预占 / 候补队列
- 物联网传感器占座
- 活动区 E1/E2 的日常散客选座（仅活动排期占用）

## 2. 已锁定决策

| 议题 | 决策 |
|---|---|
| 谁选位置 | 用户自选 |
| 库存单位 | **座位**（非整桌独占） |
| 时间模型 | **固定时段 × 座位** |
| 多人规则 | **必须同桌且连座** |
| 用户端态 | **三态**：可约 / 已约 / 不可约 |
| 店主端态 | **四态**：空闲 / 已预约 / 体验中（含剩余时长） / 维护中 |

## 3. 方案对比与选择

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 时段 × 座位矩阵（选用） | 每个 `日期+时段+座位` 一格库存 | 与现有时段、套餐时长、计时最好接；冲突易测 |
| B. 连续时间轴占座 | 自选开始时间，按时长占座 | 重叠计算重，开业过早 |
| C. 仅余量不选座 | 用户看剩余座位数，店主分座 | 不满足「点对点」 |

**选用 A。**

## 4. 领域模型

### 4.1 桌与座位

沿用现有桌号，为每桌生成有序座位：

| 区域 | 桌号 | 容量 | 日常可选 |
|---|---|---:|---|
| 窗边区 | W1, W2 | 4 | 是 |
| 日常体验区 | A1–A4 | 4 | 是 |
| 长桌区 | L1 | 8 | 是 |
| 活动区 | E1, E2 | 12 | 否（活动排期占用） |

座位标识：`{tableCode}-{index}`，index 从 1 起沿桌顺序编号，例如 `W1-1` … `W1-4`。

**连座定义：** 同一 `tableCode` 内，座位 index **连续**（差值均为 1）的一段。四边桌不按环形首尾相连（`1` 与 `capacity` 不相邻），避免歧义。

### 4.2 时段库存

固定时段（方案 A，墙钟无缝）：

- `10:00-12:00`
- `12:00-14:00`
- `14:00-16:00`
- `16:00-18:00`
- `18:00-20:00`
- `20:00-22:00`

库存键：`(appointmentDate, timeSlot, seatId)`。同一键至多一条有效预约占用。

### 4.3 预约与占座

预约在现有字段上增加：

- `tableCode`：所选连座所属桌
- `seatIds`：有序座位 ID 列表，长度 = `peopleCount`

提交时原子校验：所选座位均在该时段可约，且构成同桌连座。

### 4.4 与计时的关系

- 预约确认后：座位在对应时段为「已预约」。
- 到店开始计时：座位进入「体验中」；剩余时长由 `expected_end_at - now` 计算（复用现有预计结束逻辑）。
- 结束体验 / 取消 / 爽约释放：座位回到空闲（若无其他占用）。
- 店主可手动「维护中」锁座，用户端合并为「不可约」。

## 5. 状态机

### 5.1 用户端展示（三态）

| 展示 | 条件 |
|---|---|
| 可约 | 座位启用，且该时段无预约占用，且非维护，且当前未在体验中占用该座 |
| 已约 | 该时段存在有效预约占用该座 |
| 不可约 | 维护中，或正在体验中占用，或活动区未开放日常选座 |

用户只能点击「可约」座位；已约 / 不可约仅展示。

### 5.2 店主端展示（四态）

| 展示 | 条件 | 附加信息 |
|---|---|---|
| 空闲 | 无预约占用且未在体验且非维护 | — |
| 已预约 | 有未来/当前时段预约，尚未开始计时 | 预约人昵称脱敏可选、时段 |
| 体验中 | 存在进行中的 table_session 覆盖该座 | **剩余分钟数** |
| 维护中 | 店主锁座 | 备注可选 |

## 6. 选座交互

### 6.1 用户流程

1. 填姓名、手机、套餐、日期、时段、人数（沿用现表单）。
2. 进入选座区：按区域分组展示日常可选桌；每桌展示座位块。
3. 系统根据 `peopleCount` 计算每桌合法连座组合；点击座位时：
   - 若尚未选满：加入选择，仅允许扩展为合法连座前缀/后缀；
   - 或提供「一键选中」某段合法连座。
4. 选满 `peopleCount` 个座位后可提交。
5. 摘要增加：桌号 + 座位列表 + 预计结束时间。

### 6.2 校验规则

- `peopleCount` ≥ 1，且 ≤ 单桌最大日常容量（L1=8）；超过则提示拆单或联系包场。
- 所选必须同桌、连座、全部可约。
- 切换日期 / 时段 / 人数时清空已选座位。

### 6.3 店主流程

- 座位图：四态着色；体验中显示剩余时间。
- 可操作：锁维护 / 解锁、从预约进入开始计时（计时仍可按桌会话，会话绑定 `seatIds`）。

## 7. 数据与模块边界

### 7.1 Seed / 配置

- `tables`：保留
- 新增 `seats`：由 tables 展开生成（或静态列出日常座）
- 新增示例占用：`seatOccupancies`（日期+时段+seatId+类型）供页面与测试

### 7.2 纯函数（`miniprogram/utils/`）

建议独立 `seats.js`（或挂在 `business.js` 若保持单测入口简单）：

- `buildSeatsFromTables(tables, options)`
- `getSeatUserStatus(seat, occupancyContext)` → `available | booked | unavailable`
- `getSeatAdminStatus(seat, occupancyContext)` → `idle | reserved | in_use | maintenance`
- `findContiguousCombos(tableSeats, peopleCount, isAvailable)`
- `isContiguousSameTable(seatIds, seatsById)`
- `assertCanBookSeats({ date, slot, seatIds, peopleCount, occupancies })`

### 7.3 页面

- 修改：`miniprogram/pages/appointment/*` — 选座 UI + 提交带 seatIds
- 修改：`miniprogram/pages/admin/appointments/*` 或 `admin/timer/*` — 店主座位四态（本版优先在 timer/预约管理其一落地座位图）

### 7.4 测试

- `tests/seats.test.js`：连座、三态/四态映射、冲突拒绝、切换清空规则的纯函数覆盖

## 8. 错误与边界

| 场景 | 处理 |
|---|---|
| 提交时座位刚被占 | 拒绝，提示刷新座位图 |
| 人数 > 所有桌容量 | 提交前禁用选座，提示联系店主包场 |
| 某桌空闲但无足够连座（中间被占） | 该桌不可形成合法组合，座位保持可点但无法凑满时提示 |
| 活动桌 E | 日常图不展示 |

## 9. 验收标准

1. 给定日期+时段，用户能区分可约 / 已约 / 不可约，并完成同桌连座预约摘要。
2. 单元测试覆盖：连座判定、非法跨桌/非连座拒绝、占用冲突拒绝、用户三态与店主四态映射。
3. 店主端至少一处可看到座位四态；体验中展示剩余时长（可用 mock session）。
4. 不引入连续时间预约；不改变现有套餐时长与预计结束时间计算公式。

## 10. 风险

| 风险 | 缓解 |
|---|---|
| 座位图信息过载 | 用户端坚持三态，文案短 |
| 中间座位被占导致碎片 | 接受开业现实；后续再考虑店主拼座工具 |
| 无后端并发 | 本版本地/单测逻辑先行；接云开发时对 `(date,slot,seatId)` 加唯一约束 |
